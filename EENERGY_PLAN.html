A clear plan for the PowerTrace-Sim paper

What we want to prove, what must happen first, and what different people can build at the same time.

First fix one 250 ms work timeline. Then build the simple power model. Token-aware learned models follow on the same timeline.

The paper has three goals

Each goal needs its own test. We should not mix them into one large claim.

1

Build the simple power model first

We first need one trusted link from work done by the GPU to measured power. This becomes the base for every later model.

2

Capture fast power swings

We want to know which model best keeps the sharp one-second changes seen during AI inference.

3

Show the range of site loads

We want to repeat the site simulation and show how traffic timing changes peaks, ramps, and sustained load.

Main wording rule: We will show ranges for clearly stated scenarios. We will not call them limits for every data center.

Simple definitions

Load duration curve
A power trace sorted from highest to lowest. It shows how often the load stays above each power level.
Monte Carlo
Run the same scenario many times with different random choices. Then show the middle and outer results.
Traffic sync setting
A number called rho. A low value means servers receive bursts at different times. A high value means bursts happen together.
Measured timing
Use the request start and finish times recorded during a real run.
Arrival-only timing
Predict request work using only arrival time, input length, output length, and the server setup.
Offered tokens
Input and output tokens attached to a request when it arrives. They describe demand, not when the GPU does the work.
Executed tokens
Input or output tokens the GPU actually processes during one time window.
Sealed test
A final test whose power data stays hidden until the model and pass rules are fixed.

The critical path

The large simulation is not the first task. The models and timing must be trusted first.

1
Fix one work timeline. Use 250 ms windows. Put arrivals, input work, output work, waiting work, and power on the same clock.
2
Run one small profiling test. Prove that clocks, power, server counters, and request records line up before using more GPUs.
3
Fit the simple power model. Measure idle, input work, output work, long context, sudden steps, and two GPU group sizes.
4
Test token-aware learned models. Start with arrivals plus input and output work. Add waiting and long-context memory only if tests improve.
5
Test request timing and overload. Keep arrivals unchanged. Let unfinished requests remain waiting. Never hide overload by dropping work.
6
Run site tests. Start with a small run, then 240 servers. Add 2,400 only if the faster method gives the same answer.

Two traffic tests only

1. Exact replay

Each real request goes to one random server. No request is copied or removed.

Purpose: Keep one direct use of the public Azure day.

2. Shared-burst test

Make one-second request counts. Keep the slow shape of the day. Change how often server bursts happen together.

Keep input and output lengths paired. Keep average work per server fixed.

Important: Azure does not tell us the real server-to-server sync. The shared-burst test is a clear "what if" study.

How repeated runs become load curves

For each run

  1. Build one full site power trace.
  2. Make one-second, one-minute, and fifteen-minute versions.
  3. Sort each trace from highest power to lowest.
  4. Save peaks, ramps, average power, energy, waiting work, and failures.

Across runs

  1. Compare curves at the same point.
  2. Show a lower curve, middle curve, and upper curve.
  3. Keep each Azure day visible.
  4. Give every day the same weight.
Start
Use 3 repeats for the first speed and memory test.
Grow
Add repeats in groups of 10. Use at least 30 and no more than 200.
Tail rule
Do not show the upper 95% result until there are at least 100 accepted repeats for that case.
Stop rule
If more repeats still move the answer too much, report that fact. Do not hide it by mixing days together.

What we will not build for the main paper

These items add work but do not strengthen the three main answers enough.

Later

24,000 servers

The storage and run cost are too high before the smaller method is proven.

Later

Mixed server fleets

Routing between different GPUs and models is a separate paper-sized problem.

Later

Cached agent runs

We first need measured engine state and a correct cache model.

Later

Grid optimization

A power trace can feed a grid study later. It is not needed to prove this model.

Later

Very rare tail claims

We will not show 99% results without enough repeated runs.

Later

Many traffic models

We will start with exact replay and one clear shared-burst test.
